# LocalSend 断点续传能力：代码阅读与方案分析

- 分析对象：上游 [localsend/localsend](https://github.com/localsend/localsend)（本仓库的二次开发基线）
- 分析基线：commit `c5bbe36`（`docs: update version compatibility table (#3477)`），app 版本 `1.18.2+64`，协议版本 `PROTOCOL_VERSION_V2 = "2.2"`
- 阅读范围：`packages/core`（协议/HTTP/客户端/服务端）、`packages/localsend_isolates`（FRB + isolate）、`app/lib`（发送/接收/持久化）、`cli`、内嵌 web 页面、现有测试
- 结论性质：**可行性分析 + 改造方案**，未修改任何上游代码

---

## 0. 摘要（TL;DR）

1. **现在完全没有断点续传**：v2 协议里 `POST /api/localsend/v2/upload` 只有 `sessionId/fileId/token` 三个查询参数，语义是"把整个文件从字节 0 发一遍"；接收端 `File::create`（截断）后按 `FileDto.size` 做**全量**长度校验和**全文件** SHA-256 校验。任何中断都等于从头再来。
2. **唯一存在的"重试"是校验和 422 自动重发**（最多 3 次，整文件重发）；UI 上手动重试复用旧 `remoteSessionId` + 旧 token，而接收端在传输失败时已把该文件置为 `Failed` 且**不会再回到 `Pending`**，因此手动重试实际上会拿到 403，是一条死路（见 §3 R3/R4）。这本身就是一个可独立修复的 bug。
3. **续传所需的关键事实**：接收端在中断后**会保留残留文件**（[server_isolate.dart:699-705](../packages/localsend_isolates/lib/src/isolate/child/server_isolate.dart#L699-L705) 注释明说），但没有任何跨会话/跨重启的记录（`_ReceiveSession.targets` 只在内存里），也没有 `.part` 命名；发送端的 fileId 每次发送随机生成（[send_provider.dart:101](../app/lib/provider/network/send_provider.dart#L101)），所以**文件身份必须用内容特征（sha256/size/name）来锚定**，不能用 fileId。
4. **推荐方案（方案 A）**：接收端主导的"偏移量协商"扩展，分阶段落地（P0-P3，P4 可选），**协议向后兼容双向成立**（旧发送端忽略新字段、旧接收端忽略新 query 参数），不需要保活会话、不需要改会话生命周期：
   - 新响应字段 `resume: {fileId: {offset}}`（接收端告诉发送端"我已经有多少字节"）
   - 新可选 query 参数 `&offset=N`（发送端只发尾部），服务端以请求为准，缺省 0 → 截断重收（老发送端安全）
   - Rust 写入器支持"从 offset 追加 + 前缀哈希 + 全文件校验"，失败时上报已落盘字节数
   - 接收端新增"未完成传输档案"（partial store，持久化到 app 支持目录），并以内容特征为键
   - 发送端重试改为"重新 prepare-upload + 按 offset 续传"
5. **最大的三个坑**：① 接收端 512 KiB `BufWriter` + 进程被硬杀时，进度计数可能领先磁盘最多 512 KiB，**续传偏移必须以磁盘实际长度为准**；② Android SAF 走 `"wt"`（截断）fd，续传需要 `"rwt"`/seek，且部分第三方 provider 的 fd 不可 seek；③ 上游 `AGENTS.md` 明确限制 AI 生成贡献，提交前需要先走 issue/discussion。

## 0.1 实现状态（滚动更新）

| 阶段 | 状态 | 落地内容 |
|---|---|---|
| **P0** | 未单独实现（被 P1/P2 的重新协商覆盖） | 上游 [PR #3462](https://github.com/localsend/localsend/pull/3462) 正在处理同一问题；本仓库在 P2 让"失败文件重新 prepare-upload"成为续传路径 |
| **P1** | 已实现，待编译与集成测试验证 | 协议：`prepare-upload` 响应新增可选 `resume:{fileId:{offset}}`；`/upload` 新增可选 `offset`。落盘：`offset>0` 时不截断、校验磁盘前缀、读完前缀喂哈希后追加，终局仍是全文件 SHA-256；失败时上报已落盘字节数（`SaveOutcome.written`）。已加 6 个集成测试（见 §10） |
| **P2** | 待开始 | 接收端未完成档案（内存）、发送端按偏移续传、进度语义修正 |
| **P3** | 待开始 | 未完成档案持久化、`.part` 命名与启动对账 |

**P1 的实际协议语义**（与 §6.1 一致，已按实现固定）：

| 发送端行为 | 服务端处理 |
|---|---|
| 不带 `offset` | 视为不使用续传扩展：把会话记录的偏移重置为 0，**截断重收**（旧客户端因此永远成功） |
| 带 `offset=N` | 必须满足 `N == 会话记录的偏移` 且 `N <= 文件大小`，否则 **400**（防止错位写入损坏文件）；通过后从 N 追加 |

**关键实现细节**：

- 接收端在决策时给出的偏移会被 `min(offset, file.size)` 夹取，避免陈旧档案导致必然 400；
- 前缀哈希通过读取目标文件本身完成（同一文件句柄，SAF 描述符也可用），读到不足 `offset` 即失败 → 上层可退回从 0 重传；
- `FileUploadTarget::Stream`（应用自行消费字节）**不支持续传**，`offset > 0` 直接失败，宁可报错也不写坏文件；
- 进度 `written` 从 `offset` 起算（续传时不再倒退），且**最终值必达**（末次用 `send` 而非 `try_send`），接收端据此记录下次的续传偏移。

## 2. 现行传输全链路

### 2.1 发送端（Flutter → Rust）

1. `SendNotifier.startSession`（[send_provider.dart:88-101](../app/lib/provider/network/send_provider.dart#L88-L101)）：生成**本地** `sessionId = uuid.v4()`，给每个文件分配**随机的** `id = uuid.v4()`；随后按 `createChecksums`（默认 true，[persistence_provider.dart:397](../app/lib/provider/persistence_provider.dart#L397)）在 Rust 侧逐个文件算出 **全文件 sha256**（[send_provider.dart:166-232](../app/lib/provider/network/send_provider.dart#L166-L232)）。
2. `prepareUpload`（[send_provider.dart:261](../app/lib/provider/network/send_provider.dart#L261)）：`POST /api/localsend/v2/prepare-upload`，body 为 `{info, files:{fileId: FileDto{id,fileName,size,fileType,sha256,preview,metadata}}}`。
3. 接收端返回 `{sessionId, files:{fileId: token}}`（仅被接受的文件），本地保存为 `remoteSessionId` + 每文件 `token`（[send_provider.dart:353-404](../app/lib/provider/network/send_provider.dart#L353-L404)）。
4. `_sendFiles`（[send_provider.dart:593-626](../app/lib/provider/network/send_provider.dart#L593-L626)）：把所有文件塞进**一个** isolate 任务（内部并发 2，[upload_isolate.dart:146](../packages/localsend_isolates/lib/src/isolate/child/upload_isolate.dart#L146)），逐文件调用
   `POST /api/localsend/v2/upload?sessionId=&fileId=&token=`，body 是 `FileContent` 的**流式**字节（[client/mod.rs:181-193](../packages/core/src/http/client/mod.rs#L181-L193)：`reqwest::Body::wrap_stream`，**chunked、无 Content-Length**）。
   - `FileContent::Path` 固定从 0 读到 EOF，**没有任何 seek/offset**（[transfer.rs:60-81](../packages/core/src/model/transfer.rs#L60-L81)、[:104-130](../packages/core/src/model/transfer.rs#L104-L130)）。
   - 进度 = 已推入 body 的字节 / 全文件大小（[api/http.rs:114-133](../packages/localsend_isolates/rust/src/api/http.rs#L114-L133)）。
5. 失败处理：
   - 仅 HTTP 422（校验和不匹配）会在 isolate 内自动重发，**每次都是从 0 重发整个文件**，最多 3 次（[upload_isolate.dart:163-202](../packages/localsend_isolates/lib/src/isolate/child/upload_isolate.dart#L163-L202)）。
   - 其他错误 → 文件标记 failed，会话进入 `finishedWithErrors`（[send_provider.dart:666-698](../app/lib/provider/network/send_provider.dart#L666-L698)）。
   - UI 的"重试"按钮（[progress_page.dart:443-455](../app/lib/pages/progress_page.dart#L443-L455)）调用 `sendFile(isRetry: true)`，**复用旧的 remote session + 旧 token**，不重新协商（[send_provider.dart:543-587](../app/lib/provider/network/send_provider.dart#L543-L587)）。

### 2.2 接收端（Rust → Dart）

1. `prepare_upload`（[server/v2.rs:226-360](../packages/core/src/http/server/v2.rs#L226-L360)）：
   - 抢占**唯一会话槽**（`Mutex<Option<SessionStateV2>>`，[server/mod.rs:64-65](../packages/core/src/http/server/mod.rs#L64-L65)）；已有会话 → 409。
   - 发 `PrepareUpload` 事件给 Dart，Dart 决定接受哪些 fileId（[server/v2.rs:301-310](../packages/core/src/http/server/v2.rs#L301-L310)）。
   - 为每个被接受文件生成随机 `token`，会话进入 `Active`，响应 `{sessionId, files:{fileId:token}}`。
2. `upload`（[server/v2.rs:362-453](../packages/core/src/http/server/v2.rs#L362-L453)）：
   - 校验 `sessionId` + `fileId` + `token` + 来源 IP，且 `file.status == Pending`（[v2.rs:390-399](../packages/core/src/http/server/v2.rs#L390-L399)）后才置 `InProgress`。
   - 发 `FileUpload{session_id,file_id,file,target_tx}` 给 Dart；Dart 解析落盘目标（path 或 Android SAF fd）后 `respond_file_upload`。
   - `save_req_to_target`（[save.rs:106-247](../packages/core/src/http/server/common/save.rs#L106-L247)）把 body 边转发边哈希，写入器 `write_file_from_receiver`（[save.rs:284-355](../packages/core/src/http/server/common/save.rs#L284-L355)）：
     - `File::create`（**截断**，[save.rs:131](../packages/core/src/http/server/common/save.rs#L131)）→ `BufWriter`(512 KiB) 顺序写；
     - 结束校验 `written == expected_size`（[:315-319](../packages/core/src/http/server/common/save.rs#L315-L319)）；
     - SHA-256 比对（[:225-233](../packages/core/src/http/server/common/save.rs#L225-L233)）→ 不匹配返回 422；
     - 成功才 `set_len(written)` + 应用时间戳（[:329-352](../packages/core/src/http/server/common/save.rs#L329-L352)）。
   - `UploadGuard`：请求被中断（drop）时把文件置 `Failed`（[v2.rs:606-641](../packages/core/src/http/server/v2.rs#L606-L641)）。
   - `finalize_file`（[v2.rs:653-692](../packages/core/src/http/server/v2.rs#L653-L692)）：只有**校验和不匹配且 attempts<3** 才回到 `Pending` 允许重传；其余一律 `Failed`；文件全部 Finished|Failed 时 `is_complete()` → 会话槽清空并结束（[session.rs:40-47](../packages/core/src/http/server/common/session.rs#L40-L47)）。
3. Dart 落盘目标（[server_isolate.dart:647-663](../packages/localsend_isolates/lib/src/isolate/child/server_isolate.dart#L647-L663)）：
   - 同一会话内重试 → 复用 `session.targets[fileId]`（`reopenFileSaveTarget`），因此"重试覆盖同一个文件、不产生 name (2)"。
   - 新会话 → `prepareFileSaveTarget` → 目录内重名时用编号循环生成 `name (2).ext`（[file_saver.dart:246-250](../packages/localsend_isolates/lib/src/task/server/file_saver.dart#L246-L250)），**残留的半截文件会被当成"已存在文件"从而把新传输挤到 `name (2)`**。
4. 中断后：**半截文件留在目标目录里**，不做删除/改名/记录（[server_isolate.dart:699-705](../packages/localsend_isolates/lib/src/isolate/child/server_isolate.dart#L699-L705)）。

### 2.3 关键不变量（设计必须在这些约束下工作）

- **只有一个接收会话**，且失败即销毁；没有"部分完成"状态。
- 落盘目标由 Dart 决定、Rust 执行；Rust 只知道"写这个 path/fd"，不知道业务身份。
- 全链路校验依赖**单次全文件 SHA-256**（发送端在 prepare 前算，接收端边收边算）。
- 接收端 token 只存在于 Rust 会话里和发送端内存里，**从不持久化**。
- 进度是"已写入字节 / 全文件大小"，语义上从 0 开始。

## 4. 设计目标与约束

**目标**

- G1 网络中断/对端重启/信号切换后，能从接收端已有字节处继续，而不是重传整个文件。
- G2 接收端 app 重启后仍可续传（尽力而为：目标可达、非相册 cache 路径）。
- G3 完整性不降级：最终仍要验证**全文件 SHA-256**（当发送端提供了 `sha256` 时）。
- G4 双向兼容：新老版本任意组合都不出错、不产生损坏文件。
- G5 不引入会话保活 / 不长期占用单会话槽、不改变现有 UI 主流程（重试按钮直接变成"续传"）。

**约束**

- C1 只能通过 v2 的既有端点扩展（v3 目前只有 nonce 交换，路由见 [server/mod.rs:677-686](../packages/core/src/http/server/mod.rs#L677-L686)；不新增 v4）。
- C2 `PrepareUploadResponseDtoV2.files` 是 `Map<String,String>`（fileId→token），**不能改变其形状**，否则老客户端解析失败；偏移必须放在**新增的、可缺省**的字段里。
- C3 serde 未启用 `deny_unknown_fields`（已核对），因此新增字段对旧端天然安全；旧端忽略新增 query 参数。
- C4 能力发现只能靠**响应字段是否存在**，不能靠 `version` 字符串（该字段只是信息性的，`2.0/2.2` 混报）。
- C5 偏移量的最终权威是**接收端磁盘**，不是发送端记录、也不是进度计数。

## 5. 方案选型

| 方案 | 思路 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 接收端主导的 offset 协商**（推荐） | prepare-upload 响应新增每文件 `offset`；upload 新增 `&offset=`；Rust 追加写 + 前缀哈希 | 不碰会话生命周期；天然跨重启（配合 partial store）；双向兼容；改动集中在既有端点 | 需要 FRB 与 Dart 状态穿透；需要持久化 partial 表 | ✅ 采用 |
| B. 会话保活/重连 | 中断后保留 Rust 会话 + token 一段时间，同 token 再次 upload | 改动小 | 单会话槽被长期占用、阻塞其他发送方；接收端重启即失效；仍需 offset | 作为 A 的一个"快路径"补充（可选） |
| C. tus/`Content-Range` 风格新端点 | `HEAD /upload` 探测 + `PATCH` 分块 + `Upload-Offset` | 语义最规范、可分块校验 | 需要新端点/新路由，偏离 v2 规范，上游评审成本最高 | 备选（若要并入协议 v3） |
| D. 只做 UI 层"重新发送" | 不改协议 | 无 | 不满足需求 | ❌ |

**为什么 A 不需要保活会话**：接收端把"未完成传输"建模为**内容档案**（partial store），而不是会话状态；续传时走一次**全新的 prepare-upload**，新会话/新 token 由 Rust 正常签发，发送端只多拿一个 offset。这样 R3/R4 不用改（老行为保持），跨重启也自然成立。

## 6. 推荐方案（A）详细设计

### 6.1 协议扩展（向后兼容）

**响应新增字段**（[dto_v2.rs:99-116](../packages/core/src/http/dto_v2.rs#L99-L116)）：

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct PrepareUploadResponseDtoV2 {
    pub session_id: String,
    pub files: HashMap<String, String>,          // 不变：fileId -> token
    /// 新增：接收端对"可续传文件"已持有的字节数；无条目 = 从 0 开始
    #[serde(default, skip_serializing_if = "HashMap::is_empty")]
    pub resume: HashMap<String, ResumeInfoV2>,   // fileId -> { offset }
}

#[derive(Debug, Clone, Copy, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct ResumeInfoV2 { pub offset: u64 }
```

**上传请求新增可选参数**：

```
POST /api/localsend/v2/upload?sessionId=..&fileId=..&token=..[&offset=N]
```

**服务端规则（关键，保证双向安全且语义无歧义）**：

- 会话里为每个被接受文件保存 `resume_offset`（接收端希望的偏移，由 Dart 决策给出，默认 0）。
- 请求语义只有两条，发送端可自由二选一：
  - **带 `&offset=N` → 续传**：只有当 `N == file.resume_offset` 且 `N <= file.size` 时才接受，从 N 处追加写；否则 **400**（防止乱序/错位追加导致文件损坏，属"快速失败"）。
  - **不带 `offset` → 从头重收**：`File::create` 截断，按现状处理。这条同时就是老发送端的行为，因此老客户端永远成功，也为新发送端提供了"本地文件变了、想重来"的出口。
- 接收端的 `resume_offset` 因此只是"建议值"：发送端要么照做（续传），要么无视（重收）。服务端不会因为发送端无视建议而失败。

**兼容矩阵**

| 发送端 | 接收端 | 行为 |
|---|---|---|
| 老 | 老 | 现状，无续传 |
| 新 | 老 | 响应无 `resume` → 发送端从 0 发；`offset` 不附带 → 老服务端忽略未知参数 → 正常 |
| 老 | 新 | 接收端可能返回 `resume`，老发送端忽略；不带 `offset` → 服务端归零截断重收 → 正常 |
| 新 | 新 | 续传生效 |

> 浏览器上传页同样走 `prepare-upload` → 逐文件 `POST /upload`（[upload.html:283-305](../packages/core/assets/web/upload.html#L283-L305)）。它可以作为"新发送端"参与：对 `File` 对象 `slice(offset)` 后带上 `&offset=`。但页面刷新后 `File` 对象丢失，所以只支持"页面未关时的瞬时重试"（阶段 4，可选）。

### 6.2 Rust core 改造

**(a) 会话与决策**

```rust
// session.rs
pub(crate) struct SessionFileV2 {
    pub(crate) dto: FileDto,
    pub(crate) token: String,
    pub(crate) status: FileStatusV2,
    pub(crate) attempts: u8,
    pub(crate) resume_offset: u64,        // 新增
}

// v2.rs
pub enum PrepareUploadDecisionV2 {
    Accept(HashMap<String, u64>),         // fileId -> 期望偏移（0 = 从头）
    Decline,
}
```

`PrepareUpload` 事件可额外携带每个文件的 `resume_offset`（由 Dart 侧 store 查得）；响应组装时把 `offset > 0` 的文件放进 `resume`。

**(b) 落盘目标与写入器**（[save.rs](../packages/core/src/http/server/common/save.rs)）

```rust
pub enum FileUploadTarget {
    Stream { ... },
    Path { path: PathBuf, result_tx: ..., progress_tx: ..., offset: u64 },   // 新增 offset
    Fd   { fd: RawFd,    result_tx: ..., progress_tx: ..., offset: u64 },   // 新增 offset
}
```

- 打开方式：`OpenOptions::new().create(true).write(true).open(path)`（**不 truncate**）；`offset == 0` 时显式 `set_len(0)` 或保留 `truncate(true)`；`offset > 0` 时 `seek(SeekFrom::Start(offset))`。Fd 路径同样 `seek`。
- **前缀哈希**：`offset > 0` 时，先把文件 0..offset 读一遍喂给 `Sha256`（同时天然校验"文件长度 ≥ offset"，读短了 → 报错让上层退回 0 重传）；随后再 `update` 新收到的尾部字节 → 终局仍是**全文件哈希**。
  - 优化（可在阶段 3 做）：进程内缓存"内容键 → (offset, Sha256 状态)"，同一次运行内的重试无需重读前缀；跨重启则退回磁盘重读。
- 计数与校验：`written` 从 `offset` 起算；`written == file.size` 才算完成；`set_len(file.size)`。
- **失败回报落盘字节数**：把 `oneshot::Sender<Result<(), String>>` 改为携带 `written`（例如 `Result<(), (String, u64)>` 或一个新的 `SaveOutcome { written, error }`），并把 `SaveResult` 扩展为携带 `written`。这是 R9 的修复，也是"续传偏移正确"的前提。
- `SaveResult::HashMismatch` 语义不变（422，允许同会话重传）。

**(c) 路由与校验**（[server/v2.rs:362-453](../packages/core/src/http/server/v2.rs#L362-L453)）
读取可选 `offset`，按 §6.1 的规则决定 `effective_offset`（带 offset 必须与 `resume_offset` 相等，否则 400；不带则为 0 并截断），透传给 `save_req_to_target`。

**(d) 事件扩展**：`ServerEventV2::FileUpload` 增加 `offset: u64`，让 Dart 知道"这次要追加还是截断"。

### 6.4 Dart 接收端

**(a) 未完成传输档案（partial store）**

新增 `PartialTransferStore`（建议位置：`packages/localsend_isolates/lib/src/task/server/` 或 app 侧 provider，落盘为 app 支持目录下的 JSON）：

```jsonc
{
  "key": "sha256:ab12…",                 // 有 sha256 用它；否则 "meta:<fileName>|<size>|<lastModified>"
  "senderFingerprint": "AB12…",
  "destinationDirectory": "/storage/…/Download",
  "fileName": "video.mkv",
  "size": 5368709120,
  "offset": 3221225472,                   // 以磁盘实际长度为准（见 R10）
  "target": { "kind": "path", "path": "/…/video.mkv.part" },
  "updatedAt": 1759200000
}
```

要点：

- 查询键 = `senderFingerprint + destinationDirectory + 内容键`，避免"另一个设备/另一个目录"误续传。
- 条目 TTL + 手工清理（设置页"清理未完成传输"），避免 `.part` 无限堆积。
- 相册路径（cache 目录）不建条目（R11）。

**(b) 决策阶段带出 offset**：`prepare-upload` 到达后，用 store 查每个 offered 文件 → `Accept{fileId: offset}`；没命中就是 0。穿透 `IsolateHttpServerPrepareUploadDecisionAction`（[actions.dart:369-398](../packages/localsend_isolates/lib/src/isolate/parent/actions.dart#L369-L398)）→ `respond_prepare_upload`。

**(c) 落盘阶段**：`_handleFileUpload`（[server_isolate.dart:619-736](../packages/localsend_isolates/lib/src/isolate/child/server_isolate.dart#L619-L736)）在 `FileUpload.offset > 0` 时复用 store 里的 target（**不要**再跑 `prepareFileSaveTarget` 的重名编号逻辑，否则半截文件会被挤到 `name (2)`），并以 `respondFileUpload(offset: N)` 让 Rust 追加。

**(d) 完成/失败**：成功 → 删除 store 条目（若采用 `.part`，rename 成最终名）+ 写接收历史；失败 → 用 Rust 回报的 `written` 更新 store。app 启动时对 path 类条目做一次对账（`File.length()` 取 min），SAF 类条目则依赖 Rust 前缀读校验兜底。

**(e) `.part` 命名（建议但可分期）**
- path 目标：写 `name.ext.part`，成功后 `rename` 成 `name.ext` + 保留重名编号逻辑；好处是**不会再有"半截文件冒充完整文件"**，也不会污染重名编号。
- SAF 目标：需要新增 `DocumentsContract.renameDocument` 通道；若 provider 不支持，退化为"沿用 store 记录、不加 `.part`"（保持现状语义）。两者都可以工作，`.part` 只是更干净。

### 6.5 Dart 发送端

- `HttpUploadFile`（[upload_isolate.dart:27-41](../packages/localsend_isolates/lib/src/isolate/child/upload_isolate.dart#L27-L41)）新增 `offset`；`_sendFiles`（[send_provider.dart:602-612](../app/lib/provider/network/send_provider.dart#L602-L612)）按响应里的 `resume` 填充；`SendingFile` 记录 `offset`。
- 进度语义：`sent / (size - offset)` 或直接 `(offset + sent) / size`，UI 的 `progress*size` 聚合（[progress_page.dart:197-200](../app/lib/pages/progress_page.dart#L197-L200)）按后者更自然。
- **重试路径重写**（顺带修 R4）：`sendFile(isRetry: true)` 不再直接用旧 token，而是对"失败文件集合"重新 `prepare-upload`（可只带失败文件），拿到新 session/token/offset 后续传；保留自动重试上限与退避，避免无限循环。
- 发送端跨重启续传需要持久化 `SendSessionState`（目标设备、文件列表与路径、远端 session、offset）——建议放到阶段 4，作为一个独立特性。

### 6.6 完整性与安全

- 完整性：全程只用 `FileDto.sha256`（发送端在 `createChecksums=true` 时总会提供，默认开）。续传时接收端重读前缀得到全文件哈希 → 与现状等价（G3）。若发送端没提供 sha256（用户关掉了"创建校验和"），退化为"长度 + 前缀一致性"校验，需要在 UI 上说明。
- 身份：store 条目绑定 `senderFingerprint`（HTTPS 下用证书指纹，不可伪造，见 [AGENTS.md](../AGENTS.md) 的说明），防止别的设备接管半截文件。
- 不新增攻击面：`offset` 超界/不匹配直接 400；不信任发送端声明的 offset（以会话记录为准）。
- 路径安全：复用现有 `sanitizeRelativeName` 与目录穿越检查（[file_saver.dart:173-197](../packages/localsend_isolates/lib/src/task/server/file_saver.dart#L173-L197)）。

### 6.7 进度语义修正

现状 `written / file_size` 从 0 计（[save.rs:294-308](../packages/core/src/http/server/common/save.rs#L294-L308)、[api/server.rs:538-560](../packages/localsend_isolates/rust/src/api/server.rs#L538-L560)）。续传时如果仍从 0 计，UI 会先"倒退"到 0 再爬到 100%。需要：`progress = written_total / size`（`written_total = offset + 本次写入`），并且通知栏聚合（[receive_controller.dart:293-319](../app/lib/provider/network/server/controller/receive_controller.dart#L293-L319)）与进度页共用同一语义。

**协议规范**（[localsend/protocol v2.2 README](https://github.com/localsend/protocol)）：`/prepare-upload`、`/upload`、`/cancel`、`/prepare-download`、`/download` 全部**没有任何 offset / Content-Range / 分块 / 续传语义**；`/upload` 的请求体就是裸二进制。规范里唯一的"版本协商"是 discovery/register 报文里的 `version` 字符串（`"2.0"` 这类 major.minor），加上一个可选的 `download` 能力位，**没有任何通用的能力协商机制**——这印证了 §4 C4：能力发现只能靠"响应里是否出现新字段"。官方实现里唯一的版本判断是 `api_route_builder.dart` 的 `version == '1.0' ? v1 : v2`。

**协议仓库的关键讨论**：[localsend/protocol#31 "Proposal: Default to Resumable Download Endpoint"](https://github.com/localsend/protocol/issues/31)（open）。提案建议改用带 `Range`/`Content-Range` 的下载端点（参考 tus.io），maintainer **Tienisto 回复（2025-10-10）**：之所以用"上传"方向，是因为**发送端是发起方**，只需要接收端开放防火墙；对可续传下载表示"Resumable downloads are nice though..."，**未做任何承诺**。对我们的意义：
- 我们的方案**保持"发送端发起上传"这一方向**，因此在架构上不与维护者的顾虑冲突——这一点在对外说明里要正面写出来；
- v3 目前只是 WIP：[protocol/v3](https://github.com/localsend/protocol) 只有两个 mermaid 图、没有文字规范，代码侧 `packages/core/src/http/server/v3.rs` 的 `register` 还写着 `// TODO: not wired up yet`，因此**不能把续传挂在 v3 上等**。

**第三方实现**：[meowrain/localsend-go](https://github.com/meowrain/localsend-go) 的路线图里 `- [ ] 文件传输断点续传` 仍是未勾选状态；其余兼容实现（localsend-rs、localgo、lsq、localsend-cli 等）在 README/源码中都没有 resume/range/partial 相关能力。

**历史事实**：仓库全历史中 `git log -S '.part'` 无任何命中——**上游从来没用过 `.part` 机制**，中断后残留字节直接留在最终文件名下（这正是 #2493 想清理的问题）。

**贡献政策**（[CONTRIBUTING.md:5-9](../CONTRIBUTING.md#L5-L9) 与 [AGENTS.md:3-7](../AGENTS.md#L3-L7)）：

> LocalSend disallows AI generated contributions unless: they are bug fixes or very small or you prove your expertise in your field

按这条政策，**一个大型的、AI 撰写的续传特性 PR 三条豁免都不占**，被拒的概率很高。结论：**先走 issue/discussion 再提 PR**；对外贡献优先以"bug fix"形态交付（这也正是 P0 与 #3462 的定位），协议扩展部分需要人工评审、并提前与 maintainer 对齐字段命名与是否并入下一版协议。

## 9. 风险与开放问题

1. **上游贡献政策**：`AGENTS.md` 明确"AI 生成的贡献除非是 bug fix / 很小 / 能证明专业性，否则不被接受"。建议：先把 P0 当作 bug fix 提 PR（附复现），同时开 issue/discussion 讨论协议扩展；协议字段命名与是否并入 v3 需要与 maintainer 对齐（协议规范在独立仓库，改动会更慢）。
2. **SAF 可 seek 性**：`DocumentsContract` 的 fd 对本地文档通常可 seek，云盘 provider 不一定；必须保留"读前缀失败 → 退回 0 重传"的兜底，否则会写出花屏文件。
3. **硬杀一致性**（R10）：偏移必须以磁盘长度为准；`.part` + 启动对账是最稳的组合。
4. **前缀重读成本**：续传一个 10 GB、已收 9.9 GB 的文件，接收端需要再读约 9.9 GB 来喂哈希（SSD 数十秒）。可用"进程内 hasher 缓存"与"每 N MiB 检查点复算"两级优化；也可以考虑发送端在 prepare 时附带"前缀摘要"——但那会把成本转移到发送端，且需要新的可信来源。
5. **磁盘占用/残留清理**：`.part` + store 需要 TTL、设置项与"清理未完成传输"入口，否则用户磁盘会积累。
6. **多文件并发 vs 单会话**：现有单会话槽不变，续传不引入新的并发问题；但如果 P0 的"重新 prepare-upload"发生在旧会话尚未被接收端清理时，会撞 409（接收端只在全部文件 Finished|Failed 时释放槽位）。
7. **`ReceiveController` 的"保持会话打开"语义**（[receive_controller.dart:413-415](../app/lib/provider/network/server/controller/receive_controller.dart#L413-L415)）与 Rust 会话已被销毁的事实不一致，P0 需要顺带核对。
8. **测试基建**：Dart 侧（app/isolates）目前没有发送/接收的单元测试；核心逻辑必须落在 Rust 集成测试里（`packages/core/tests/`），Dart 侧新增 store 的单测。
9. **未验证项**：本文所有结论来自本地代码阅读；未真机复现"断网重试 403"（结论由代码路径推出：`Failed` → 403，见 R3/R4），实施前建议先按复现步骤确认一次。

### 13.4 实现前必须先定的 4 个真实摩擦点

1. **校验和的归属（fd 只能被消费一次）**：现在哈希在 `save_req_to_target` 里做，而文件句柄在 writer task 里才创建（fd 走 `File::from_raw_fd` 被移动，[save.rs:141-161](../packages/core/src/http/server/common/save.rs#L141-L161)）。续传要先读前缀喂哈希，因此必须二选一：
   - **推荐**：把"写 + 哈希 + 长度校验"整体移进 writer task，由它返回 `written` 与摘要/结果（结构更干净，顺带解决 R9）；
   - 或者对 SAF fd 用 `libc::dup`（`libc` 已是 unix 依赖）复制一个只读句柄读前缀，path 目标则另开只读句柄。
2. **前缀重读的成本**：续传一个 10 GB / 已收 9.9 GB 的文件，接收端需要再顺序读约 9.9 GB 来得到全文件哈希（SSD 数十秒）。优化路径：进程内缓存"内容键 → (offset, `Sha256` 状态)"（同一次运行内的重试零成本）+ 每 N MiB 检查点复算。
3. **有界重试与逃生舱**：若磁盘上前缀已损坏，每次续传都会 422 → 死循环。必须规定"同一 offset 连续 K 次哈希失败后丢弃 partial、强制从 0 重收"（探针 5a/5b 已覆盖该路径）。
4. **409 时序**：P0 的"重新协商"前应尽力 `POST /cancel` 旧会话，否则旧会话尚未被接收端清理时会撞 `409 Blocked by another session`（[v2.rs:255-268](../packages/core/src/http/server/v2.rs#L255-L268)）；`/cancel` 在会话已结束时只会落到 `CancelReceived` 分支，无副作用（[v2.rs:491-524](../packages/core/src/http/server/v2.rs#L491-L524)）。

### 13.5 这些情况下"不可行"（范围否决条件，而非技术障碍）

- **要求不改协议 / 纯客户端实现**：不可行。接收端必须能"按 offset 追加写"并"告知已有字节"，否则发送端无从得知断点。
- **要求 WebRTC 通道也支持续传**：当前 WebRTC 只有接收端信令（[webrtc_receiver.dart](../app/lib/provider/network/webrtc/webrtc_receiver.dart)），文件通道未打通，本次范围外。
- **要求"换网/换 IP 后完全无感、且不落任何中间状态"**：不可行。跨会话续传必须持久化 partial 元数据（内容键 + 偏移 + 目标）。
- **要求兼容第三方非官方实现的私有行为**：无法验证，只能按协议规范做保守假设。

### 13.6 MVP 与建议顺序

**最小可用切片**：P0（修 403 死路）+ P1（core offset 能力）+ P2（同一次运行内的续传、路径目标、`.part` 暂不做），约 **1.5-2 周**，能在两台真机上演示"断网 → 重试 → 从断点继续"。把 SAF 细节、跨重启 store、发送端会话持久化留到 P3/P4。

建议顺序：装工具链跑一次 baseline（`cargo test --features full`）→ 确认上游 [PR #3462](https://github.com/localsend/localsend/pull/3462) 的状态（它无协议改动地解决同一问题）→ 复现并修 P0（上游最可能接受，注意不要与 #3462 重复）→ 提 issue 附 §6.1 的字段提案（并正面回应协议仓库 [#31](https://github.com/localsend/protocol/issues/31) 里"为什么用上传方向"的顾虑：本方案保持发送端发起，不影响防火墙前提）→ 再推进 P1。
